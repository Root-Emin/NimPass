# Purchase payment QR — scanner capability investigation

**Date:** 2026-09-16
**Question:** can a QR scanned with **Nimiq Pay → Pay → Scan** produce a NIM
transaction that carries the Nimpass purchase reference (`NP1:<32 hex>`) in its
transaction data, so the backend can bind exactly one on-chain transaction to
exactly one Purchase Intent without weakening any existing check?

This document records evidence, not intentions. Two answers are needed before
the scanner-first flow can be built, and they are independent:

| Gate | Question | Answer today |
|---|---|---|
| **G1 — scanner** | Does the Nimiq Pay payment scanner accept a Nimiq request link, and does its `message` reach the transaction's data field? | **UNRESOLVED — undocumented; measured by the probe in §6** |
| **G2 — discovery** | Can the Nimpass backend learn about a payment nobody reported to it? | **YES — implemented. §4 described the blocker; §5's work has since landed. See ADR-010.** |

G2 is cleared: `getTransactionsByAddress` discovery, the `Discover` writer and
the discovery sweep are implemented (ADR-010), so a payment made in Nimiq Pay
with nobody to report it is now found by the server and verified by the
unchanged pipeline.

G1 is still unmeasured, and the payment QR ships anyway — because ADR-010
removed the failure it was guarding against. The original worry was a scan that
pays without the `NP1:` reference and can therefore never be matched; discovery
now settles such a payment on the sender/recipient/exact-value/window tuple, and
the Mini App opener remains on the same screen as a second route. Walking §6 is
still worth doing: it would tell us whether the reference reaches the chain on
this path, which is the stronger correlation when it is available.

---

## 1. What the official sources say

Read on 2026-09-16:

- [Mini Apps overview](https://nimiq.dev/mini-apps) — documents exactly two
  openers, `nimiqpay://miniapp?url=…` and
  `https://nimpay.app/miniapps/open/…`. These are **navigation**, not payment.
  The page says nothing about QR codes or the in-app scanner.
- [Request Link Encoding](https://nimiq.dev/nimiq-utils/request-link-encoding)
  — the official NIM request-link formats, e.g.
  `nimiq:NQ48…5XJ8?amount=100&message=Payment`.
- [`RequestLinkEncoding.ts`](https://github.com/nimiq/nimiq-utils/blob/master/src/request-link-encoding/RequestLinkEncoding.ts)
  — the encoder itself: three NIM types (`safe` https, `nimiq:` URI,
  `web+nim://` URI), `amount` in **decimal NIM**, `message` URI-encoded and
  **capped at 64 bytes** ("see `BasicAccount.verifyIncomingTransaction` in
  Nimiq core").
- [Nimiq Wallet `ScanQrModal.vue`](https://github.com/nimiq/wallet/blob/master/src/components/modals/ScanQrModal.vue)
  — the **web wallet's** scanner accepts a bare address, any NIM request link
  (URI or Safe), BTC and EIP-681. Evidence about the ecosystem's conventions,
  **not** about Nimiq Pay, which is a separate closed-source app.
- [Mini Apps FAQ](https://nimiq.dev/mini-apps/faq) — no mention of QR, the
  scanner, or payment requests.

**No official document states which QR payloads the Nimiq Pay scanner accepts.**
That is the whole reason this file exists.

## 2. What the app itself says

Observed on a real device, 2026-09-16, scanning the current Nimpass desktop QR
(`nimiqpay://miniapp?url=…`) with Nimiq Pay's payment scanner:

> Invalid link format. Only CPLinks and NAKA requests for NIM and Bitcoin
> Lightning requests are supported.

and, as the scanner's own hint text:

> Scan any supported Nimiq, USDT, Bitcoin Lightning or NAKA QR code to pay.

These two strings do not agree with each other. "CPLinks and NAKA" is a closed
list that excludes plain Nimiq request links; "any supported Nimiq … QR code"
implies they are included. The error is also the *rejection* path for a Mini App
deep link, which tells us what the scanner is **not** for, not exactly what it
is for.

Neither string is a specification, so neither is treated as one here.

Context on the two named schemes:

- **CPLink** = [cplink.com](https://cplink.com) (formerly cryptopayment.link).
  Its current links are **hosted orders** — `https://cplink.com/pay/<id>`,
  resolved by CPLink's own backend, which owns the order, its return URLs and
  its chain watching. Adopting it would put a third-party service inside the
  Nimpass payment path and would not, by itself, put `NP1:` into the
  transaction data.
- **NAKA** = a third-party merchant acquiring scheme ([naka.com](https://naka.com)),
  not something a mini app issues.

Neither is a route to "our reference in the transaction data".

## 3. NP1 audit (the value that must survive)

| Property | Value |
|---|---|
| Generated by | backend only — `NewPaymentReference()`, `backend/internal/domain/values.go:130` |
| Format | `NP1:` + 32 lowercase hex (16 random bytes); legacy `NP:` accepted on parse |
| Length | **36 bytes ASCII** — fits the 64-byte Nimiq data limit and the 64-byte request-link `message` cap |
| Reaches the customer via | `paymentRequest.data` in the purchase DTO, `backend/internal/httpapi/payment_handlers.go:45` — present **only** while `status == awaiting_payment` |
| Today's path onto the chain | mini app → `sendBasicTransactionWithData({ value, data })` |
| Verified by | `validateEvidence`, `backend/internal/application/payment.go:192` — `recipientData` decoded and compared **byte-for-byte** with the intent's reference |

No shortening, hashing or re-encoding is possible: the backend compares the raw
bytes. A request link's `message` is transported URI-encoded and must arrive as
the same 36 ASCII bytes.

## 4. The proven blocker: Nimpass cannot discover a payment

This is settled by reading the code, not by testing a device.

1. Verification starts from a **hash the client reported**:
   `Payments.Reconcile` returns immediately when there is no candidate hash —
   `backend/internal/application/payment.go:86`.
2. The background reconciler only walks purchases that **already have** a
   candidate row: `Due()` joins `payment_candidates`,
   `backend/internal/database/payment.go:18`.
3. The chain adapter can only look a transaction up **by hash**:
   `RPCClient.Inspect` → `getTransactionByHash` / `getTransactionFromMempool`,
   `backend/internal/nimiq/rpc.go:155`. There is no address query anywhere in
   the backend.
4. `validateEvidence` additionally requires a submission timestamp inside the
   intent's lifetime (`p.SubmittedAt`), so a payment with no submission record
   cannot pass even if a hash appeared by other means.

In the scanner-first flow **nobody reports the hash**: the payment happens in
Nimiq Pay's own UI, outside any Nimpass surface, on a different device from the
desktop that is waiting. So today the transaction would be paid and then never
seen. This is independent of which QR format the scanner accepts.

One thing that is *not* a blocker: `POST /purchases/{id}/submissions` does not
require a wallet-dispatch lock (`Submit`, `backend/internal/database/payment.go:191`).
It needs only `PAYMENT_PENDING` before expiry, is idempotent for the same hash
and conflicts on a second one. The hash has always been an untrusted hint that
the server re-verifies — so **whoever** supplies it, the security model is
unchanged.

## 5. Required backend work (Model B — server-side discovery)

**Implemented (ADR-010).** The table below is what was specified; it landed
close to as written, with two deliberate differences noted after it.

| # | File | Change | Reason |
|---|---|---|---|
| 1 | `backend/internal/nimiq/rpc.go` | Add `TransactionsByAddress(ctx, address, max, startAt)` calling `getTransactionsByAddress` (official PoS JSON-RPC; needs a **history or full** node — the address-indexing requirement is the only new infrastructure constraint). Reuse the existing `result.data` envelope, network and consensus checks. | The only primitive that can find a transaction nobody reported. |
| 2 | `backend/internal/application/payment.go` | New `DiscoverDue` pass: for purchases in `PAYMENT_PENDING` with **no** candidate, query the intent's `Snapshot.Recipient`, keep transactions whose decoded `recipientData` equals the intent's `PaymentReference` **exactly**, and adopt that hash as the candidate. Then run the **unchanged** `Inspect` + `validateEvidence` + `Confirm` path. | Discovery replaces the client's hash report; verification stays identical. |
| 3 | `backend/internal/database/payment.go` | `Due()` (or a sibling `DueForDiscovery()`) must also return pending purchases with no candidate row, rate-limited the same way; a `Discover()` writer creates the candidate with `submitted_at = discovered_at` under the same row lock and `ErrConflict` rules as `Submit`. | `validateEvidence` requires a submission time; discovery must supply one truthfully. |
| 4 | `backend/internal/domain/purchase.go` | No change required. `PAYMENT_PENDING → TRANSACTION_SUBMITTED → VERIFYING → AWAITING_FINALITY → CONFIRMED` already models the lifecycle, and `ReconcileVerified` already accepts server-discovered evidence. | Keep the state machine as the authority. |
| 5 | `backend/openapi.yaml` | Document that `transactionHash` may appear without a client submission. No new endpoint is needed for the happy path. | The desktop already polls `GET /purchases/{id}`. |

Two deliberate differences from the specification above, both recorded in
ADR-010:

- **The reference is optional, not required, for a discovered match.** §5 as
  written kept `recipientData == NP1` mandatory. That would mean a scanner
  which drops `message` takes real NIM and produces nothing. Discovery now
  matches on the sender/recipient/exact-value/network/window tuple when the data
  field is **empty**, and still refuses a transaction carrying any *other*
  reference. This is what let G1 stop being a blocker.
- **Ambiguity is refused.** If two transactions match one intent, neither is
  adopted; guessing which of a customer's two transfers settles a purchase is
  not a decision code should make.

Two invariants to state explicitly in that work:

- **Uniqueness.** A reference is 16 random bytes and one intent; adopting a
  discovered hash must go through the same "one candidate per purchase,
  conflict on a second" rule, and the existing unique constraint on verified
  payments still prevents one transaction settling two purchases.
- **Sender.** `validateEvidence` line 183 still requires
  `sender == ExpectedWallet`. Scanner-first removes the mini app's
  "check selected wallet" step, so the desktop screen must show *pay from this
  wallet* prominently. A payment from another wallet is rejected on purpose;
  that must not be softened into "any sender with the right reference".

## 6. The probe (clears G1)

`frontend/web/scripts/nimiq-pay-scan-probe.mjs` renders one QR per candidate
format — all with the same recipient, amount and a realistic `NP1:` reference —
into a self-contained page:

```bash
cd frontend/web
node scripts/nimiq-pay-scan-probe.mjs --address "NQ.. your own testnet address"
open nimiq-pay-scan-probe.html
```

| # | Candidate | Payload |
|---|---|---|
| A | Bare address | `NQ…` |
| B | `nimiq:` URI, amount | `nimiq:NQ…?amount=1` |
| C | **`nimiq:` URI, amount + message** | `nimiq:NQ…?amount=1&message=NP1%3A<32 hex>` |
| D | Safe/wallet request link | `https://wallet.nimiq.com/#_request/NQ…/1/NP1%3A<32 hex>_` |
| E | `web+nim://` URI | `web+nim://NQ…?amount=1&message=NP1%3A<32 hex>` |

Procedure, on the device, with Nimiq Pay switched to **Testnet**:

1. Nimiq Pay → **Pay** → scanner → scan each code from the screen.
2. Record per candidate: accepted or rejected (**exact** error text), and if
   accepted whether recipient, amount and the reference-as-message are shown.
3. Also capture **Nimiq Pay → Receive with an amount** as a screenshot. Whatever
   format Nimiq Pay itself emits is a format its own scanner must read — that
   screenshot is direct evidence of the app's native request-link format.
4. Only if a candidate is accepted **with the reference visible**: send it once
   on Testnet and read the transaction's data field back from the chain. A
   message shown in the UI is not proof it reaches `recipientData`.

## 7. What each outcome means

- **G1 passes** (a format is accepted *and* its message lands in
  `recipientData`) → build scanner-first: the desktop QR becomes that payment
  request, built only from `paymentRequest` (recipient, `valueLuna` → decimal
  NIM, `data`), and the backend work in §5 lands with it. The Mini App openers
  stay, for navigation only.
- **G1 fails on the message but passes on the payment** (accepted, no data
  field) → scanner-first is **not** usable for Nimpass: without `NP1:` on
  chain, matching would fall back to recipient+amount+time, which
  `validateEvidence` refuses and which §14 of the mission forbids. The mini app
  payment path stays the only settlement route; the desktop QR stays a Mini App
  locator (ADR-005) and the copy must send the customer to the phone camera,
  never to Nimiq Pay's scanner.
- **G1 fails entirely** → same conclusion, with a stronger reason.

## 8. End-to-end Testnet validation (only once G1 and G2 are cleared)

Desktop creates the intent → payment QR appears → Nimiq Pay → Pay → Scan →
prepared transaction shows the Nimpass recipient and the exact amount → confirm
→ backend discovery adopts the hash → `validateEvidence` (sender, recipient,
value, `NP1:`, network, execution) → macro-block finality → `CONFIRMED` → Pass
created → the desktop page, which polls `GET /purchases/{id}` continuously while
in `INTENT_CREATED` (`frontend/web/src/hooks/use-purchase-flow.ts:286`), moves
to the pass without any action on the desktop. A refresh must resume the same
intent through `/purchases/:id`.

The payment QR itself contains no Nimpass URL, so this works with the frontend
on `http://192.168.x.x:5173`; only the backend needs the Testnet RPC node.
